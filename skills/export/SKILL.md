# Competitive Research — Export

Use this when the user wants the shortlist *out of the report and into where work actually happens*. The analysis already writes `report.json` for exactly this purpose; without an export step that file just sits there.

Never invent recommendations here. This skill only moves what a prior run already produced. If the numbers look wrong, the fix is to re-run the analysis, not to edit them on the way out.

## Workflow

### 1. Find the report

Look for the newest `./competitive-research/runs/*/report.json`. If none exists:

> No report to export yet. Run the analysis first (say *"run the competitive research"*), then come back.

Then exit.

If the newest report is more than 14 days old, say so and ask whether to export it anyway or re-run the analysis first. Stale recommendations create stale tickets.

### 2. Confirm the target

Ask which destination, and default to whatever the repo supports:

> **Where should these go?**
> 1. **GitHub issues** — one issue per feature (needs the `gh` CLI, authenticated)
> 2. **Markdown checklist** — a single file you can paste into Linear/Notion/Jira
> 3. **CSV** — one row per feature, for a spreadsheet or an importer

Check `gh auth status` before offering option 1. If `gh` is missing or not authenticated, say so plainly and offer options 2 and 3 instead — do not try to install anything.

### 3. Confirm the scope

Show the shortlist as a numbered list — rank, name, RICE, Strategic Fit, tag — and ask:

> **Export all N, or just the top few?** (e.g. "top 5", "1,3,7", "all")

Default to the top 5 if the user says "go ahead" without picking. Exporting all ten at once tends to create a backlog nobody triages.

Skip anything already tagged `RECURRING` whose history entry is `in-progress` — there is likely a ticket for it already. Mention what you skipped and why.

### 4. Create the output

**GitHub issues.** One issue per feature. Title is the feature name. Body:

```markdown
_Generated by /competitive-research:export from the YYYY-MM-DD analysis run._

**What:** [description]

**Why now**
- Shipped by: [competitor, competitor]
- JTBD advanced: [jtbd_advanced]
- Kano class: [kano_class]
- User pain: [user_pain]

**Evidence**
- "[quote]" — [source_url]

**Scores**
| RICE | Reach | Impact | Confidence | Effort | Strategic Fit |
|---|---|---|---|---|---|
| 1240 | 800/qtr | 2 | 80% | 1 pm | 8/10 |

**Where this lands**
- `src/path/to/file.ts`
- `app/path/`

**MVP wedge:** [mvp_wedge]

**Risks:** [risks]
```

Create each with `gh issue create --title "..." --body-file <tmpfile>`. Write bodies to temp files rather than passing them inline — the bodies contain quotes, backticks, and newlines that break shell escaping.

Apply a `competitive-research` label to every issue so they are filterable later. Create the label first if it does not exist (`gh label create competitive-research --color BFD4F2 --description "Sourced from competitive analysis"`); ignore the error if it already exists.

**Markdown checklist.** Write `./competitive-research/runs/YYYY-MM-DD/export.md` — one `- [ ]` per feature with name, RICE, Strategic Fit, one-line description, and the landing files indented under it.

**CSV.** Write `./competitive-research/runs/YYYY-MM-DD/export.csv` with a header row: `rank,name,tag,rice,strategic_fit,kano_class,jtbd,description,mvp_wedge,codebase_landing,risks`. Quote every field — descriptions contain commas.

### 5. Record what was exported

Append to `./competitive-research/history/exports.jsonl` (create if missing), one line per exported feature:

```json
{"date": "2026-08-17", "feature_name": "Single sign-on (SAML)", "target": "github", "ref": "https://github.com/org/repo/issues/42", "run_date": "2026-08-17"}
```

This is what stops a later run from exporting the same feature twice. Before creating anything in step 4, read this file and warn about features already exported:

> **Already exported:** "Bulk CSV import" went out on 2026-08-10 as issue #38. Export again anyway?

### 6. Confirm

Print what was created — issue URLs, or the file path — and remind the user:

> Mark these with `/competitive-research:track` once you decide what to build. Anything marked `shipped` or `wontfix` drops out of future shortlists.

## Quality bar

- **Never create issues without showing the list and getting an explicit go-ahead.** Issue creation is outward-facing and noisy to undo.
- **Never fabricate a field.** If `report.json` has no `user_quotes` for a feature, omit the Evidence block rather than inventing a quote.
- **Mirror the report exactly.** Scores, names, and evidence must match `report.json` character-for-character. This skill is a transport, not an author.
- **One issue per feature.** Do not bundle "the top 5" into a single tracking issue unless the user asks.
- Check `exports.jsonl` before creating. Duplicate tickets are the fastest way to make the user stop trusting this.
